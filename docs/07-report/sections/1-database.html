1. Database design

Two databases, as the PRD asks. MySQL keeps the fixed, related data: users, their sessions, and orders. MongoDB keeps the book catalog and its reviews, which are searched far more often than changed. Each service owns its own data and no app touches a database.

1.1 Entities and attributes

EntityDatabase, ownerAttributes (PK primary key, FK foreign key, UQ unique)
users
an account		MySQL, user-servicePK id INT · username VARCHAR(50) UQ · email VARCHAR(255) UQ · password_hash CHAR(60) (bcrypt, never the password) · role CUSTOMER or MANAGER · created_at
sessions
a login		MySQL, user-servicePK token CHAR(64) (random) · FK user_id · created_at. Deleted at log out (FR2)
orders
an order		MySQL, order-servicePK id INT, from 1001, printed on the bill · FK user_id · payment_status PENDING or PAID · total DECIMAL(10,2) · bill_file · created_at
order_items
one book in an order		MySQL, order-servicePK id · FK order_id · book_id CHAR(24) (a MongoDB id) · title, author (copied, so the bill never changes) · type BUY or RENT · quantity > 0 · unit_price DECIMAL(10,2) · rent_due_date (RENT only)
books
a book		MongoDB, book-service_id ObjectId · title · author · price · copiesAvailable · coverUrl (optional) · category (one of 5 shelves). The rating is worked out from the reviews on each search, never stored
reviews
a customer's review		MongoDB, book-service_id · bookId · userId (a MySQL user id) · username · rating 1 to 5 · text (up to 1000) · createdAt · updatedAt. UQ (bookId, userId): one review per customer per book
