1. Database design

Mooney's keeps its data in two databases, both named bookstore. MySQL holds the users, their sessions, and the orders. MongoDB holds the book catalog and the reviews. Each service owns its own data: user-service owns users and sessions, order-service owns orders and order_items, and book-service owns books and reviews.

Everything below is read from the schema script database/mysql/schema.sql and from the code that reads and writes the data: JdbcUserRepository and JdbcSessionRepository in user-service, MySqlOrderRepository in order-service, and MongoBookRepository and MongoReviewRepository in book-service.

1.2 Why two databases

DatabaseHoldsWhy
MySQL 8.0users, sessions, orders, order itemsThe structure is fixed and the tables are related. An order and its items must be saved together as one transaction, or not at all.
MongoDBbooks, reviewsBooks are simple documents that are searched by keyword far more often than they are changed. Reviews belong to books, so they sit next to them, in the same service.

The PRD fixes which service uses which database. The reasons above are from docs/02-design/architecture.md ("Why each database", and decision 25 for reviews).

1.5 MongoDB collections

1.5.1 books

One document per book (FR4, FR5, FR14). Owned by book-service. Field names are in camelCase, the same as in the JSON the API returns.

FieldTypeRequiredMeaning and rules (checked by book-service before saving)
_idObjectIdyes (made by MongoDB)The book's id; the API sends it as 24 hex characters
titleStringyesNot empty, at most 255 characters
authorStringyesNot empty, at most 255 characters
priceNumberyesGreater than 0, at most 100,000. A price saved through the API is a double rounded to two decimals. A whole-number price loaded from books.json is stored as an integer; book-service reads both as a decimal number
copiesAvailableNumber (integer)yes0 or more, at most 1,000,000. A manager sets it when editing the book (FR14). An order takes copies in one atomic step (PATCH /api/books/{id}/copies), which refuses to go below 0, so two orders cannot both take the last copy
coverUrlString or nullnoAddress of a cover photo (starts with http:// or https://, at most 2000 characters). Without it the apps draw a cover from the title
categoryStringyes for a new or changed bookThe shelf: one of Fiction, Nonfiction, Kids, Science, Technology. A book stored before shelves existed may have none

Indexes: _id (MongoDB's own), and one on title and one on author, created by database/seed.py when it loads the books (a first set-up or a full reset). A book's rating (ratingAverage, ratingCount in the API) is not stored; it is worked out from the reviews each time, so it can never drift from them.

1.5.2 reviews

One document per customer per book (course section-6 extra credit). Owned by book-service.

FieldTypeRequiredMeaning and rules

Indexes: _id, and the unique index one_review_per_customer_per_book on (bookId, userId). book-service creates it at start-up, and again before the first write if MongoDB was not reachable at start-up. The index is what makes "one review per customer per book" true even when two saves arrive at the same moment.

1.6.1 Keeping references correct across the two databases

No database can check a reference into the other one, and MongoDB does not check references at all. The services keep them correct instead:

ReferenceKept correct by
order_items.book_id → books._idorder-service never trusts a book id from the app. For each book in an order it calls book-service (PATCH /api/books/{id}/copies), which takes the copies in one atomic step and answers with the book. If the book does not exist (404) or has too few copies (409), nothing is saved. The title, author, and price saved in the item come from that answer.
reviews.bookId → books._idBefore a review is read, saved, or deleted, book-service looks the book up and refuses with 404 if it does not exist. It saves the book's own id, so one book is never kept under two spellings of its id.
reviews.userId → users.idThe user id and username are never taken from the request. book-service asks user-service who owns the session token, and uses the answer. Only a logged-in customer can write a review; a manager is refused (403).
orders.user_id → users.idA normal MySQL foreign key. The id itself also comes from user-service's answer about the token, not from the request.

No endpoint deletes a book or a user, so in normal use these references cannot be left pointing at nothing. The demo-data script removes its customers' reviews from MongoDB in the same run that removes the customers from MySQL. A full reset of the test data (python database/seed.py, without --if-empty) replaces every book with a new _id; old order items still show the right title and price, because those were copied, but old reviews then refer to books that are gone.
