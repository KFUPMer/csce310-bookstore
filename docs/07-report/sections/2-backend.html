2. Backend design: the REST API

The backend is three services. Each one owns its own data and answers HTTP requests with JSON. The two apps talk only to these services, never to a database. This section first gives the rules that every endpoint follows, then lists all 20 endpoints, then shows each one with a sample request and response.

Everything here was read from the code as it is now: the user-service handlers (AuthHandler, UserHandler, BaseHandler, the request records), and the routes.py, schemas.py, models.py, services.py, auth.py and errors.py of book-service and order-service. The design document docs/02-design/api-design.md says the same.

2.1 Common rules

2.1.1 The three services

ServiceBase URLBuilt withOwnsURL prefixes
user-servicehttp://localhost:8081Java 21, com.sun.net.httpserver.HttpServerUsers and sessions (MySQL)/api/auth, /api/users
book-servicehttp://localhost:8082Python, Flask, run by waitressBooks and reviews (MongoDB)/api/books
order-servicehttp://localhost:8083Python, Flask, run by waitressOrders and order items (MySQL); bill files (bills/ folder)/api/orders, /api/reports

Each service listens on this machine only, on both 127.0.0.1 and ::1. The ports can be changed with the settings USER_SERVICE_PORT, BOOK_SERVICE_PORT and ORDER_SERVICE_PORT; the numbers above are the defaults.

2.1.2 Requests and responses

  • Request bodies and responses are JSON. The one exception is the bill (GET /api/orders/{id}/bill), which is HTML.
  • Field names are in camelCase, for example copiesAvailable and paymentStatus.
  • Dates are YYYY-MM-DD. Times are YYYY-MM-DDTHH:MM:SS, in whole seconds.
  • Money is a JSON number. Python writes 40.00 as 40.0, so the samples below show it that way.
  • A request body may be at most 16 KB.

2.1.3 Logging in and the token

A user logs in once with POST /api/auth/login and gets a session token: 64 random hexadecimal characters. Every other request, except register and the copies endpoint that only order-service calls (2.4.5), must carry it in this header (N4):

Authorization: Bearer 3f9a1c0e7b2d4a6f8e1c3b5d7a9f0e2c4b6d8a1f3e5c7b9d0a2c4e6f8b1d3a5c

The token is kept in the sessions table of user-service. Logging out deletes it, so it stops working at once (FR2). Book-service and order-service do not keep sessions: they ask user-service about every token (2.1.6).

2.1.4 Roles

RoleWhoUsesMay
CUSTOMERAnyone who registersThe customer app, "Mooney's"Search books, place orders, see and pay their own orders, write reviews
MANAGERCreated by database/seed.py onlyThe management app, "Mooney's Manager"Add and change books, see all orders, set the payment status, see the sales report

Each service checks the role itself (N5). The apps hide what a role may not do, but that is only for comfort: the check that counts is in the service.

2.1.5 Errors

Every error from an API address (/api/...), in every service, has the same shape: one field, error, holding a message written for a person. The apps show this message as it is.

{ "error": "Wrong username or password" }

In the code, routes and handlers never build an error response. They throw (Java) or raise (Python) an error class that carries its status. One place per service turns it into the response: BaseHandler.handle in user-service, register_error_handlers in errors.py in the other two. An unexpected failure is logged in full and answered with a plain 500, so no SQL or stack trace ever reaches a caller.

A database failure is the one exception: create_app in app.py catches it (PyMongoError in book-service, mysql.connector.Error in order-service), logs it, and answers 503 in the same error shape. User-service has no such handler, so a MySQL failure there is a 500.

StatusMeaningError class
200OK
201Created (register, add a book, place an order)
204Done, empty body (delete a review)
400A field is missing or not acceptable; the message names it. Also: the body is not valid JSONValidationException / ValidationError
401No token, the token is not a current session, or wrong login detailsUnauthorizedException / UnauthorizedError
403Logged in, but this role may not do this, or it is someone else's order; a wrong service keyForbiddenError
404The book, order or review does not exist, or nothing is at this addressNotFoundError, ApiException.notFound, Flask
405The address exists, but not for this HTTP methodApiException.methodNotAllowed, Flask
409Username or email already used; not enough copies; order already paidConflictException / ConflictError
413Book-service and order-service only: the body is larger than 16 KB (user-service answers 400 "The request is too large")Flask
500A bug, or in user-service a failed database: "Something went wrong on the server. Please try again."Anything else
503Book-service and order-service only: something they depend on (user-service, book-service, MongoDB, MySQL) is not answering (user-service answers 500 when MySQL is down)ServiceUnavailableError

The checks run in a fixed order: the token first (401, or 503 if user-service is down), then the role (403), then the request body (400), then the data itself (404, 409). So a customer who sends a bad book to POST /api/books gets 403, not 400.

2.1.6 Calls between services

CallerCallsWhenHow it proves who it is
book-service, order-serviceGET /api/auth/session on user-serviceOn every request from an app, to learn who owns the token and their roleIt passes on the app's own Authorization header
order-servicePATCH /api/books/{id}/copies on book-serviceOnce per book when an order is placed, with a negative change; with a positive one to give copies back if the order failsThe header X-Service-Key, a secret shared by the services through their settings (SERVICE_KEY)

Order-service does not ask book-service for the price in a separate call. The copies endpoint takes the copies in one atomic step and answers with the whole book, so one call gives both the copies and the title, author and price. Two customers can never both get the last copy. Each call waits at most 2 seconds to connect and 3 seconds for an answer; after that the caller answers 503.

If no service key is set, the copies endpoint stays closed (403), and placing an order answers 503. The key is compared in constant time (hmac.compare_digest).

2.3 user-service

Two handler classes serve these endpoints: AuthHandler for /api/auth/* and UserHandler for /api/users/*. Both extend BaseHandler, which reads the body, reads the token and sends every error.

A user always comes back in this shape (the record UserResponse). The password hash is never sent. token is only present in the answer to login; elsewhere it is null, and Gson leaves null fields out.

FieldTypeNotes
tokenstringLogin only. 64 hexadecimal characters
userIdnumberThe id in the users table
usernamestring
emailstringStored in lower case
rolestringCUSTOMER or MANAGER

2.3.1 Log in

POST /api/auth/login

Anyone. Checks the username and password with bcrypt and starts a session (FR1).

Request:

{ "username": "alice", "password": "alice2026" }

Response 200:

{
  "token": "3f9a1c0e7b2d4a6f8e1c3b5d7a9f0e2c4b6d8a1f3e5c7b9d0a2c4e6f8b1d3a5c",
  "userId": 3,
  "username": "alice",
  "email": "alice@example.com",
  "role": "CUSTOMER"
}
StatusWhen
400"Enter your username" or "Enter your password"; the body is not valid JSON or empty
401"Wrong username or password". The same message whether the username or the password is wrong, so it does not tell which usernames exist

2.3.2 Log out

POST /api/auth/logout

Logged in. No body. Deletes the session, so the token stops working (FR2).

Response 200:

{ "message": "Logged out" }
StatusWhen
401"You are not logged in": no token, or it is not a current session

2.3.3 Check a session

GET /api/auth/session

Logged in. The apps do not call it: book-service and order-service call it to learn who owns a token and their role (N4, N5). No body.

Response 200:

{ "userId": 3, "username": "alice", "email": "alice@example.com", "role": "CUSTOMER" }
StatusWhen
401"You are not logged in" (no header) or "Your session has ended. Please log in again." (unknown token)

2.3.4 Register

POST /api/users/register

Anyone. Creates a customer account (FR3). A new account is always a CUSTOMER. The password is hashed with bcrypt before it is stored (N3).

Request:

{ "username": "alice", "email": "alice@example.com", "password": "alice2026" }

Rules (the record RegisterRequest): username 3 to 50 characters, only letters, digits, dots, dashes and underscores; email shaped like name@host.domain, at most 255 characters; password 8 characters or more, and at most 72 bytes (bcrypt reads no further).

Response 201, with no token (the user logs in next):

{ "userId": 3, "username": "alice", "email": "alice@example.com", "role": "CUSTOMER" }
StatusWhen
400The first field that breaks a rule, for example "The username must be 3 to 50 characters long", "Enter a valid email address", "The password must be at least 8 characters long"
409"Username or email already in use"

2.4 book-service

All endpoints are in routes.py. Every one that the apps use first checks the token with user-service. If user-service does not answer, the result is 503 "The login service is not answering. Please try again in a moment."; if MongoDB does not answer, 503 "The book catalog is not available right now. Please try again in a moment."

The book object. Every endpoint that returns a book uses this shape (Book.to_json):

2.5 order-service

The order endpoints are in create_routes and the report in create_report_routes, both in routes.py. Every endpoint checks the token with user-service first. If MySQL does not answer, the result is 503 "Orders are not available right now. Please try again in a moment."

The order object (Order.to_json). Title, author and price are copied into the order when it is placed, so an order and its bill stay correct if the book changes later.

FieldTypeNotes
idnumberThe order number
username, emailstringThe customer who placed the order, read from the users table through orders.user_id each time the order is read, so it shows the account as it is now
createdAtstringDate and time, whole seconds
paymentStatusstringPENDING or PAID. A new order is PENDING
itemslistEach: title, author, type (BUY or RENT), quantity, unitPrice (what one copy cost: the price to buy, 10% of it to rent), rentDueDate (7 days after the order for RENT, null for BUY)
totalnumberThe sum of unitPrice × quantity
billFilestring or nullWhere the bill was saved, bills/bill-{id}.html; null if the file could not be written

The order summary (Order.to_summary_json), used in lists for the manager, has only id, username, createdAt, total and paymentStatus.

2.5.1 Place an order

POST /api/orders

Customer (FR6 to FR10). The body lists the chosen books, each bought or rented. Rules (OrderInput.from_json): 1 to 50 items; bookId is 24 hexadecimal characters; type is BUY or RENT. The same book with the same type chosen twice becomes one item with quantity 2.

What happens: take the copies of each book from book-service (2.1.6), work out the charges, save the order as PENDING, write the bill file, answer, then email the bill in the background. If a book is missing or sold out, or the order cannot be saved, every copy already taken is given back and nothing is saved.

Request:

{
  "items": [
    { "bookId": "655f1c2ab7e4a1d2c3f4a5b6", "type": "BUY" },
    { "bookId": "655f1c2ab7e4a1d2c3f4a5b7", "type": "BUY" },
    { "bookId": "655f1c2ab7e4a1d2c3f4a5b8", "type": "RENT" }
  ]
}

Response 201: the whole order, plus the bill and whether it is being emailed.

{
  "id": 1042,
  "username": "alice",
  "email": "alice@example.com",
  "createdAt": "2026-11-18T10:05:00",
  "paymentStatus": "PENDING",
  "items": [
    { "title": "Clean Code", "author": "Robert C. Martin", "type": "BUY",
      "quantity": 1, "unitPrice": 40.0, "rentDueDate": null },
    { "title": "Database System Concepts", "author": "Abraham Silberschatz", "type": "BUY",
      "quantity": 1, "unitPrice": 55.0, "rentDueDate": null },
    { "title": "Java Concurrency in Practice", "author": "Brian Goetz", "type": "RENT",
      "quantity": 1, "unitPrice": 8.0, "rentDueDate": "2026-11-25" }
  ],
  "total": 103.0,
  "billFile": "bills/bill-1042.html",
  "billHtml": "<!DOCTYPE html>...",
  "emailQueued": true
}

emailQueued is true when the bill was handed over for emailing and false when email is not set up. It does not mean the email has arrived: it is sent after the answer, so that it cannot slow the order down.

StatusWhen
400"Send the order as a JSON object", "Select at least one book", "An order can have at most 50 books", "Item 2: the book id is not valid", "Item 3: choose BUY or RENT"
401Not logged in
403"Only a customer can place an order"
404"This book does not exist"
