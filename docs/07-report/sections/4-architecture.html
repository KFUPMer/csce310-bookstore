4. Architectural and class design

This section shows how the system is split into parts, which design patterns it follows, and every class in it. The class lists were checked against the source code as it is now.

4.2 How the design follows the patterns

4.2.1 Client/server

ClientServerWhat crosses the wire
Both appsuser-serviceHTTP requests with JSON bodies; JSON answers. Log in returns a session token
Both appsbook-service, order-serviceHTTP with JSON, and the header Authorization: Bearer <token>. One exception: GET /api/orders/{id}/bill answers with the HTML bill, not JSON
book-service, order-serviceuser-serviceGET /api/auth/session with the caller's token, to learn who is asking and their role. Timeout 2 s to connect, 3 s to read; no answer becomes 503
order-servicebook-servicePATCH /api/books/{id}/copies with the header X-Service-Key, to take copies when an order is placed and give them back if it fails
order-serviceGmail SMTPThe bill as an email, sent in the background

The apps never touch a database. Each service is the only owner of its data. Errors always come back in one shape, { "error": "message" }, with the right status code. In the apps, ApiClient turns every failure into one ApiException.

4.2.2 Three tiers

TierComponentsJob
PresentationMooney's, Mooney's Manager, bookstore-uiShow data and take input. They check form fields first so the user sees a problem at once, but the services check again and have the last word
Logicuser-service, book-service, order-serviceThe rules: who may do what, prices, renting (10% of the price, 7 days), copies, bills, reports
DataMySQL, MongoDB, bill filesKeep the data. Only the logic tier reads or writes it

Gmail SMTP is outside the three tiers: it is an outside service that order-service calls.

4.2.3 The four layers inside each service

Every service is split into the same four layers (docs/02-design/engineering-rules.md, section 2). A layer calls only the layers below it; every layer may use the models and raise the errors.

LayerDoesuser-service (Java)book-service (Python)order-service (Python)
Routes / handlersRead the request, ask the login check who is calling, call the service, write JSONBaseHandler, AuthHandler, UserHandler, Json; request and response records in http/dtoroutes.py (create_routes); request shapes in schemas.pyroutes.py (create_routes, create_report_routes); request shapes in schemas.py
ServicesThe rules. No request handling and no SQL; calls to other services go through interfacesAuthService, PasswordHasher, TokenGeneratorBookService, ReviewService; the login check: auth.py and SessionChecker (asks user-service)OrderService, ReportService, pricing.py, bill.py; the login check: auth.py and SessionChecker; other services behind BookCatalog and Mailer
RepositoriesRead and write the databaseUserRepository, SessionRepository (interfaces) with JDBC and in-memory versions; DatabaseBookRepository, ReviewRepository (abstract) with MongoDB and in-memory versionsOrderRepository (abstract) with MySQL and in-memory versions; BillStore for bill files
ModelsPlain dataUser, Session, Rolemodels.py: Book, Review, RatingTotals, CurrentUsermodels.py: Order, OrderItem, SalesReport, and others

Around the layers, each service also has a start-up part (UserServer, __main__.py, app.py), its settings (Config), and its errors (error/ in Java, errors.py in Python). The start-up part is the only place that picks the real classes; tests hand in the in-memory ones instead.

The repository layer is defined by interfaces (Java) and abstract classes (Python). This is why each service can be tested without a database: the tests use the in-memory versions.

4.2.4 Model-View-Controller

The project was not built on an MVC framework. The table shows where the MVC roles fall in the code, and where the fit is loose.

PartModelViewController
ServicesThe model classes (User, Book, Order ...) with the services and repositories that hold the rules and the dataThe JSON answer (each model's to_json(), or UserResponse in Java), and the HTML bill made by render_bill()The routes and handlers: they take the request, call the service layer, and choose the answer
Flutter appsThe data classes: Book, Order, PlacedItem, Review, OrderDraft, SalesReport ...Widgets and screens: SearchScreen, OrdersView, BillView ...Controller-like: the *Api classes, Session, AppServices / ManagerServices, and each screen's State class, which reacts to a button and calls an API

Where the apps do not follow strict MVC:

  • Flutter is built from widgets. A screen's State class both draws the screen (build) and handles its events (for example SearchScreen calls BookApi.search itself). There is no separate controller class per screen.
  • Some classes notify the view directly: the models OrderDraft and Preferences, and the controller-like Session, extend Flutter's ChangeNotifier, and the app redraws when they change.
  • Some models hold small rules, such as OrderItem.charge (the rent price), and the form checks checkBook() and checkRegistration() are plain functions, not classes.

In the services, the split into routes, services, repositories, and models is stricter than MVC needs: the controller (routes) never touches the database, and the rules live in the service layer, not in the routes.

4.3 Classes

Colors in all class diagrams mean the layer. In the services: blue is HTTP (the routes, and app.py, which registers them), purple the request shapes, green the rules and what they ask of other services (the login check, book-service, the mail server), yellow storage, grey start-up, settings and plain data, red errors. In the apps: blue is screens, green the calls to the services, yellow data, grey the application, session, and rules. Private classes (names starting with _) are parts of one screen; they are listed together and not drawn.
